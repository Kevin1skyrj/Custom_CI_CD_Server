# Milestone 3: Persistent Pipeline Jobs and Logs

## Goal

Convert an accepted GitHub push into a durable pipeline job. The webhook request should return quickly, while the job metadata and its log remain available after the HTTP request finishes or the server restarts.

## Result

An authorized push now creates this structure:

```text
data/pipeline-jobs/
└── <job-uuid>/
    ├── job.json
    └── pipeline.log
```

The webhook responds with HTTP `202 Accepted` and the generated job ID. A client can then request:

```http
GET /pipeline-jobs/<job-id>
```

The response contains both the persisted job metadata and its log.

## Request flow

```text
GitHub push
  -> POST /webhook/github
  -> verify signature
  -> validate event, repository and branch
  -> webhook controller
  -> pipeline service creates job model
  -> repository writes job.json and pipeline.log
  -> 202 response containing jobId

Client
  -> GET /pipeline-jobs/:jobId
  -> pipeline controller
  -> pipeline service validates UUID
  -> repository reads job.json and pipeline.log
  -> 200 response, or 404 when no job exists
```

## Why `202 Accepted` is used

`202` means that the server accepted the request for asynchronous processing. It does not claim that installation, testing, building, or deployment succeeded. At this milestone, the job is only persisted with the `queued` status.

Returning `200` with a message such as “deployment successful” would be inaccurate because no pipeline stages have executed yet.

## Job model

Each `job.json` currently contains:

```json
{
  "id": "generated UUID",
  "deliveryId": "GitHub delivery identifier",
  "repository": "owner/repository",
  "branch": "main",
  "commitSha": "exact pushed commit",
  "status": "queued",
  "createdAt": "ISO-8601 timestamp"
}
```

### Field decisions

- `id`: Our internal identifier. A UUID avoids relying on sequential shared state.
- `deliveryId`: GitHub's identifier for this webhook delivery. Milestone 4 will use it for duplicate protection.
- `repository`: Identifies the source project.
- `branch`: Records which accepted branch caused the pipeline.
- `commitSha`: Preserves the exact source version that must be checked out later.
- `status`: Begins as `queued`; later milestones will introduce controlled transitions.
- `createdAt`: Supports auditing and duration calculations.

## File responsibilities

### `src/repositories/pipeline.repository.js`

This is the persistence layer. It knows that jobs are currently stored on the filesystem. Controllers and routes do not need to know file paths.

- `fs` from `node:fs/promises` provides non-blocking promise-based filesystem operations.
- `path` creates platform-correct paths on Windows and Linux.
- `path.resolve(PIPELINE_DATA_DIR)` turns the configured directory into one stable absolute base path.
- `savePipelineJob(job)` creates the job directory and writes readable JSON.
- `{ recursive: true }` allows directory creation even when parent directories do not yet exist.
- `appendPipelineLog(jobId, message)` adds a timestamped line without replacing previous entries.
- `findPipelineJobById(jobId)` reads and parses the stored JSON.
- `readPipelineLog(jobId)` returns the complete text log.
- An `ENOENT` error means the requested file does not exist, so read functions return `null`.
- Other filesystem errors are rethrown because permission failures or corrupted storage are server problems, not “job not found.”

### `src/services/pipeline.service.js`

This is the business-logic layer.

- `crypto.randomUUID()` creates a UUID v4 job identifier.
- `createPipelineJob(payload, deliveryId)` selects only the webhook data required by the pipeline.
- `payload.ref.slice("refs/heads/".length)` removes the already-validated branch prefix.
- The service persists metadata before appending the first log entry.
- `getPipelineJobDetails(jobId)` validates the identifier before passing it to the filesystem repository.
- The UUID v4 regular expression accepts only the identifier format generated by this application.
- UUID validation prevents values such as `../../secret-file` from becoming path segments. This blocks path traversal at the service boundary.
- The returned object combines metadata with `log`; a missing log becomes an empty string.

### `src/controllers/webhook.controller.js`

- Reads the trusted, validated GitHub delivery ID and commit SHA.
- Rejects the request with `400` if required delivery metadata is missing.
- Calls the pipeline service rather than writing files directly.
- Returns `202` with the new `jobId`.
- Converts unexpected persistence failures into a controlled `500` response.

### `src/controllers/pipeline.controller.js`

- Reads `jobId` from the route parameter.
- Calls the service to retrieve the job.
- Returns `404` for both an invalid identifier and a valid but unknown UUID.
- Returns `200` with `{ job }` when found.
- Does not expose internal filesystem errors to the client.

### `src/routes/pipeline.routes.js`

- Creates a separate router for pipeline-job operations.
- Maps `GET /:jobId` to `getPipelineJob`.
- It contains HTTP routing only; it contains no storage or business logic.

### `src/app.js`

Mounting the router at `/pipeline-jobs` combines with `/:jobId` to create:

```text
GET /pipeline-jobs/:jobId
```

### `src/config/env.js`

`PIPELINE_DATA_DIR` makes storage location configurable. Production data can use `./data/pipeline-jobs`, while tests use `./test-data/pipeline-jobs` and cannot overwrite real job history.

### `.gitignore`

`data/` and `test-data/` are ignored because runtime job records and logs should not be committed. Logs may contain repository information and can grow continuously.

## Tests added

The integration tests prove that:

1. An authorized push receives `202` and a job ID.
2. `job.json` is physically created.
3. `pipeline.log` is physically created.
4. Required webhook metadata is stored correctly.
5. The initial status is `queued`.
6. `GET /pipeline-jobs/:jobId` returns persisted metadata and logs.
7. An invalid job ID returns `404`.
8. A correctly formatted but nonexistent UUID returns `404`.
9. Test data is removed before and after the suite.
10. All Milestone 1 and Milestone 2 security behavior still passes.

## Why filesystem persistence is acceptable here

This project is intentionally small and educational. Files make job state and logs easy to inspect, require no database service, and survive process restarts.

The repository layer is still separated so its implementation can later be replaced with PostgreSQL, MongoDB, or object storage without moving storage code into controllers.

## Current limitations

These are deliberate boundaries, not hidden production claims:

- Multiple server instances cannot safely share ordinary local disk.
- Concurrent writes to the same job are not yet coordinated.
- JSON replacement is not yet an atomic temporary-file-and-rename operation.
- Logs are returned in full; pagination or streaming would be needed for very large logs.
- There is no log retention or cleanup policy yet.
- The retrieval route has no user authentication. The intended first deployment is an owner-operated private service; authentication would be required before exposing job data publicly.
- Duplicate GitHub deliveries can still create multiple jobs. Milestone 4 handles this.
- Jobs do not execute yet. Milestones 5 and 6 add checkout and pipeline stages.

## Security points

- The webhook body is verified before it is trusted.
- Repository and branch validation occurs before job creation.
- The job retrieval service accepts only UUID v4 identifiers.
- Runtime data is excluded from Git.
- API errors do not return filesystem paths or stack traces.
- Future stage output must redact secrets before it is appended to logs.

## Interview explanation

> After authenticating and validating a GitHub push, my server creates a UUID-based pipeline job and persists its metadata and timestamped logs on disk. I separated routes, controllers, services, and repositories so HTTP concerns, business rules, and storage are independent. The webhook returns 202 because it only queues work; it does not falsely report deployment success. I also expose a job retrieval endpoint and validate UUIDs before constructing filesystem paths to prevent path traversal. Filesystem persistence keeps the educational project small, while the repository abstraction leaves a clear migration path to a database.

## Expected interview questions

### Why not execute deployment inside the webhook request?

Deployments can take minutes. Keeping the request open risks GitHub timeouts and repeated webhook deliveries. Persisting a queued job allows the webhook to respond quickly and lets a worker process it independently.

### Why store the exact commit SHA?

A branch can advance after the webhook is received. The SHA gives reproducibility: the pipeline must test and deploy the exact revision that triggered the job.

### Why store GitHub's delivery ID as well as your UUID?

The UUID identifies our job. The delivery ID identifies GitHub's webhook attempt and will allow Milestone 4 to recognize retries and prevent duplicate pipelines.

### Why use a repository layer?

It isolates storage details. Services express pipeline behavior while the repository handles filesystem operations. This improves testability and makes a later database migration smaller.

### Why use append-only logs?

Pipeline output is chronological. Appending preserves prior entries and avoids reading and rewriting the entire log for each message.

### Why return `null` only for `ENOENT`?

Only a missing file means “not found.” Treating permission or I/O failures as missing data would hide operational failures and produce misleading `404` responses.

### How does UUID validation improve security?

The route parameter eventually becomes part of a path. Restricting it to UUID v4 prevents separators and `..` sequences from escaping the configured data directory.

### Would you use filesystem storage in a distributed production system?

Not as the shared source of truth. I would use a transactional database for job state and centralized or object storage for logs. This implementation is suitable for a small single-node CI/CD server and deliberately keeps that tradeoff visible.

### What happens if writing the job succeeds but writing the initial log fails?

The request currently returns `500`, although the job file may exist. A more advanced implementation could make creation transactional, retry log writes, or record logs in the same database transaction. This is a known filesystem limitation.

### Why are logs included in the job response?

It provides a small observable API without building a dashboard. For large logs, I would create a paginated or streaming log endpoint instead.
